دیدن یک syscall مشکوک و متوقف کردن عملیاتی که آن syscall می‌خواهد انجام دهد دو کار متفاوت‌اند. ابزار ردیابی می‌تواند رویداد را گزارش کند، اما گزارش به‌تنهایی **اعمال سیاست** نیست؛ تا تصمیم در فضای کاربر گرفته شود، عملیات ممکن است تمام شده باشد.

برای تصمیم در نقاط کنترل دسترسی، باید از hookی استفاده شود که قرارداد آن اجازهٔ تصمیم‌گیری می‌دهد. در لینوکس، **BPF LSM** یکی از این مسیرهاست.

## مشاهده با enforcement یکسان نیست

سه سطح را از هم جدا کنید:

۱. **Audit:** ثبت اطلاعات عملیاتی مانند اجرای process یا دسترسی به فایل.
۲. **Detection:** تحلیل این داده‌ها و تشخیص الگوی مشکوک، معمولاً با منطق فضای کاربر.
۳. **Enforcement:** پذیرش یا رد عملیات در یک hook مناسب، پیش از تکمیل آن.

یک tracepoint عادی را نباید صرفاً با تغییر مقدار بازگشتی به policy engine تبدیل کرد. نوع برنامه و hook مشخص می‌کنند چه چیزی قابل‌خواندن است و مقدار برگشتی چه معنایی دارد. برای شبکه، برنامه‌های XDP یا tc قرارداد تصمیم خود را دارند؛ برای کنترل عملیات امنیتی، hookهای LSM زمینهٔ متفاوتی دارند.

## LSM چه contextی می‌دهد؟

چارچوب **Linux Security Modules** نقاطی برای کنترل دسترسی در هسته فراهم می‌کند. BPF LSM به برنامه‌های دارای مجوز اجازه می‌دهد به hookهای پشتیبان وصل شوند و audit یا بخشی از policy را پیاده کنند.

برای مثال `bprm_check_security` در مسیر بررسی امنیت اجرای فایل برنامه است. این نقطه با «دیدن ورود به execve» یکسان نیست: hook شیء مربوط به عملیات هسته را می‌بیند و تصمیم آن بخشی از مسیر امنیتی است.

قبل از استفاده باید پیکربندی‌هایی مانند `CONFIG_BPF_LSM`، BTF مورد نیاز و فعال بودن `bpf` در مجموعهٔ LSMهای سیستم بررسی شوند. وجود object شما یا حتی وجود syscallِ BPF برای نتیجه گرفتن دربارهٔ LSM کافی نیست.

## نتیجهٔ قبلی را حفظ کنید

این **قطعهٔ audit-only** الگوی اتصال MACِ معمول BPF LSM را نشان می‌دهد و هیچ عملیاتی را خودش رد نمی‌کند:

```c
SEC("lsm/bprm_check_security")
int BPF_PROG(observe_exec, struct linux_binprm *bprm, int ret)
{
    if (ret != 0)
        return ret;

    /* Optional bounded audit logic; no new denial in this example. */
    return 0;
}
```

برای این قطعه، نوع‌های `vmlinux.h`، هدرهای `bpf_helpers.h` و `bpf_tracing.h`، تعریف license و loader مناسب لازم‌اند. در الگوی معمول MAC، `ret` نتیجهٔ برنامهٔ BPF قبلی در همان زنجیره یا صفر برای اولین برنامه است. حفظ خطای قبلی مانع آن می‌شود که منطق شما آن تصمیم را نادیده بگیرد؛ این فیلد را نتیجهٔ تمام LSMهای دیگر فرض نکنید.

همهٔ شکل‌های اتصال LSM قرارداد یکسان ندارند؛ برای مثال semantics اتصال cgroup LSM را باید جداگانه از MACِ معمول خواند. همچنین هر hook الزاماً مقدار برگشتی قابل‌استفاده برای رد عملیات ندارد.

## چرا «نام process» سیاست خوبی نیست؟

نام `comm` کوتاه، تغییرپذیر و غیرمنحصربه‌فرد است. مسیر فایل نیز به mount namespace، rename و شیوهٔ resolve شدن وابسته است. PID می‌تواند دوباره استفاده شود و شناسه‌ها در namespaceها متفاوت دیده شوند.

یک سیاست باید معلوم کند بر چه هویتی بنا شده است: cgroup، credential، inode و filesystem مورد نظر یا ترکیبی از این‌ها. دریافت دادهٔ درست در hook باید با قرارداد policy سازگار باشد؛ هیچ کلید ساده‌ای برای تمام سناریوها وجود ندارد.

همچنین ثبت رویداد و جلوگیری از عملیات دو مسیر موفقیت جدا هستند. شکست ارسال audit event به ring buffer نباید ناخواسته تصمیم دسترسی را تغییر دهد، مگر این‌که رفتار fail-open یا fail-closed از ابتدا تعریف شده باشد.

## وریفایر جای threat model را نمی‌گیرد

وریفایر برای محدود کردن اجرای برنامه و دسترسی‌های مجاز ضروری است، اما درست بودن سیاست امنیتی یا نبودن آسیب‌پذیری در کل هسته را تضمین نمی‌کند. مجوز بارگذاری BPF قدرت مهمی است و باید حداقل‌سازی شود.

در هسته‌های پشتیبان، capabilityهایی مثل `CAP_BPF`، `CAP_PERFMON` و `CAP_NET_ADMIN` نقش‌های متفاوت دارند؛ مجموعهٔ دقیق لازم به عملیات، نوع برنامه، attachment و policy سیستم وابسته است. در بعضی محیط‌ها `CAP_SYS_ADMIN` یا محدودیت‌های اضافی همچنان مطرح‌اند. دادن همهٔ capabilityها به یک container روش عیب‌یابی سالمی نیست.

## سیاست را چگونه منتشر کنیم؟

ابتدا در محیط آزمایشی و حالت audit، نرخ رویداد، موارد مثبت کاذب و افت داده را اندازه بگیرید. سپس rollout محدود با مسیر rollback و مسئولیت مشخص انجام دهید. اعمال یک قانون جدید روی میزبان مدیریت می‌تواند ابزار دسترسی، package manager یا سرویس ضروری را مختل کند.

BPF LSM را مکمل threat model، کنترل دسترسی و hardening سیستم ببینید؛ نه جایگزین خودکار SELinux، AppArmor، جداسازی یا به‌روزرسانی امنیتی.
