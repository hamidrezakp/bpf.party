یک برنامهٔ eBPF معمولاً برای هر رویداد فراخوانی می‌شود. اگر قرار باشد بین رویدادها شمارنده، سیاست یا زمان شروع عملیات حفظ شود، متغیر محلی روی stack کافی نیست. **map**ها objectهایی در هسته‌اند که برنامهٔ BPF و، با مجوز لازم، برنامهٔ فضای کاربر می‌توانند با آن‌ها کار کنند.

map فقط دیکشنری نیست: array، hash، ساختارهای per-CPU، صف و ring buffer همه زیر همین زیرساخت قرار می‌گیرند، اما عملیات و قواعدشان یکسان نیست.

## انتخاب map از روی پرسش، نه محبوبیت

| نیاز | گزینهٔ اولیه | نکتهٔ طراحی |
|---|---|---|
| چند مقدار با کلید عددی ثابت | `BPF_MAP_TYPE_ARRAY` | خانه‌ها از ابتدا وجود دارند؛ حذف عنصر ندارد |
| وضعیت با کلید پویا، مثل شناسهٔ thread | `BPF_MAP_TYPE_HASH` | ظرفیت محدود و مسیر خطای درج لازم است |
| شمارندهٔ پرتکرار روی چند CPU | `BPF_MAP_TYPE_PERCPU_ARRAY` | خواننده باید نسخه‌های CPUها را جمع بزند |
| cache با اخراج خودکار | `BPF_MAP_TYPE_LRU_HASH` | داده ممکن است با اخراج از دست برود |
| انتقال رویداد به فضای کاربر | `BPF_MAP_TYPE_RINGBUF` | قرارداد queue است، نه lookup/update معمول |

LRU جایگزین مناسبی برای وضعیت «حتماً باید تا پایان عملیات موجود بماند» نیست. اگر زمان شروع درخواست برای محاسبهٔ latency اخراج شود، خروجی پایان درخواست دیگر جفت معتبر ندارد. این فقدان را باید بشمارید، نه آن‌که به latency صفر تبدیل کنید.

## یک شمارندهٔ کوچک per-CPU

این تعریف و تابع، **قطعهٔ برنامه** برای اضافه شدن به یک hook مناسب‌اند؛ loader و attachment در آن نیست:

```c
struct {
    __uint(type, BPF_MAP_TYPE_PERCPU_ARRAY);
    __uint(max_entries, 1);
    __type(key, __u32);
    __type(value, __u64);
} counts SEC(".maps");

static __always_inline void count_event(void)
{
    __u32 key = 0;
    __u64 *value = bpf_map_lookup_elem(&counts, &key);

    if (value)
        __sync_fetch_and_add(value, 1);
}
```

هدرهای `bpf_helpers.h` و تعریف نوع‌ها لازم‌اند. lookup در سمت BPF به مقدار CPU فعلی دسترسی می‌دهد. جداسازی per-CPU رقابت بین CPUها را کاهش می‌دهد؛ در این نمونه از عملیات اتمیک استفاده شده تا افزایش ساده را با فرض نامشخص دربارهٔ reentrancy در یک hook توضیح ندهیم. استفاده از atomicها نیز باید با قابلیت‌های toolchain و هستهٔ مقصد سازگار باشد.

در فضای کاربر، برای خواندن مقدار per-CPU باید آرایه‌ای به‌اندازهٔ CPUهای **ممکن** سیستم آماده شود، نه فقط CPUهای آنلاین در آن لحظه. اندازهٔ هر value نیز در رابط syscall مطابق قواعد alignment گرد می‌شود. `libbpf_num_possible_cpus()` و رابط‌های libbpf کمک می‌کنند این قرارداد را درست پیاده کنید.

## map مشترک، شمارندهٔ مشترک

اگر همان شمارنده در یک array معمولی باشد، چند CPU ممکن است مقدار مشترکی را هم‌زمان بخوانند و بنویسند:

```c
/* A shared value: this is not an atomic increment. */
*value += 1;
```

قفل داخلی map برای عملیات ساختاری، تمام محاسبات شما روی value را به یک تراکنش تبدیل نمی‌کند. برای یک افزایش ساده، atomic مناسب می‌تواند کافی باشد. برای تغییر چند فیلد با invariant مشترک، گزینه‌هایی مانند `bpf_spin_lock` در map و نوع برنامهٔ پشتیبان یا طراحی متفاوت لازم می‌شوند؛ قفل محدودیت‌هایی دارد و هر helper یا فراخوانی دلخواه را نمی‌توان در محدودهٔ آن انجام داد.

**پذیرش وریفایر یعنی رعایت قواعد ایمنی قابل‌بررسی، نه race-free بودن منطق کاربرد.**

## خواندن metric، snapshot جادویی نیست

حتی جمع زدن مقدارهای per-CPU نیز لزوماً یک snapshot هم‌زمان از تمام CPUها نمی‌دهد. هنگام خواندن، برنامه هنوز در حال افزایش شمارنده است. برای نرخ‌ها و metricهای تقریبی این رفتار ممکن است مناسب باشد؛ برای حسابداری دقیق باید قرارداد خواندن، reset و جمع‌آوری را مشخص کنید.

الگوی «مقدار را بخوان و سپس صفر کن» می‌تواند افزایش‌هایی را که بین دو عملیات رخ می‌دهند از دست بدهد. استفاده از تفاضل دو شمارندهٔ تجمعی، با توجه به wraparound و restart، اغلب ساده‌تر است.

## ظرفیت و عمر داده بخشی از API هستند

برای هر map از ابتدا این موارد را مشخص کنید:

- حداکثر تعداد کلیدها و بودجهٔ حافظه؛ per-CPU هزینهٔ value را در تعداد CPUهای ممکن ضرب می‌کند.
- رفتار هنگام پر شدن یا شکست update: drop، retry در فضای کاربر یا کاهش جزئیات؟
- زمان حذف کلیدها؛ برای جفت entry/exit، مسیرهای خطا و خروج thread هم اهمیت دارند.
- آیا pin لازم است و هنگام restart چه چیزی باید بازسازی شود؟
- کدام طرف اجازهٔ نوشتن تنظیمات یا خواندن اطلاعات حساس را دارد؟

برای mapهای رویدادی و قرارداد مصرف‌کننده، [ring buffer و perf buffer]({% post_url 2026-10-11-ringbuf-perf-events %}) را بخوانید.
