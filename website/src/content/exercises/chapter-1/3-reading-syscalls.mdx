در تمرین‌های قبلی به scheduler (`sched_process_exec`) hook زدیم. این رویداد *بعد از* بارگذاری باینری توسط کرنل و پر کردن ساختارهای درونی آن فعال می‌شود.

اما *قبل از* آن چه می‌شود؟ وقتی برنامه‌ای مثل `bash` می‌خواهد `ls` را اجرا کند، از طریق system call `execve` به کرنل درخواست می‌دهد.

System callها با tracepointهای مشخصی که تا الان استفاده کردیم متفاوت‌اند. از رویدادهای generic `entry` و `exit` استفاده می‌کنند که برای همه syscallها کار می‌کنند.

## ساختار عمومی syscall

چون *صدها* system call (`open`, `write`, `execve`...) وجود دارد، هر کدام با مجموعه آرگومان‌های خود، کرنل برای tracepointها از یک ساختار generic استفاده می‌کند.

در رویدادهای entry، contextی با نوع `struct trace_event_raw_sys_enter` دریافت می‌کنیم:

```c
struct trace_event_raw_sys_enter {
    long int id;               /* Syscall number */
    long unsigned int args[6]; /* Arguments */
    /* ... */
};
```

فیلدهای راحتی مثل `name` یا `pid` نداریم — فقط شماره syscall (`id`) و آرایه‌ای از اعداد صحیح، `args[6]`، که آرگومان‌های system call هستند.

چرا ۶؟ چون حداکثر تعداد آرگومان‌هایی است که syscallها می‌توانند داشته باشند.

همچنین *هیچ* نوعی هم نداریم! همه آرگومان‌ها `long unsigned int` (`u64`) هستند و تفسیر درست آن‌ها (به‌صورت pointer، struct، اعداد signed یا حتی `u64`!) به خودمان بستگی دارد.

برای دانستن نوع و معنای هر آرگومان می‌توانید به [صفحه manual](https://man7.org/linux/man-pages/man2/execve.2.html) مراجعه کنید که امضا را نشان می‌دهد:

```c
int execve(const char *filename, char *const argv[], char *const envp[]);
```

چون `filename` آرگومان اول است، در `ctx->args[0]` قرار دارد. آرایه `args` آن را به‌صورت `unsigned long` ذخیره می‌کند، پس باید به `const char *` cast کنیم.

### دربارهٔ فضای آدرس

`ctx->args[0]` به حافظه‌ای که متعلق به پردازه فراخواننده است (مثلاً `bash`) اشاره می‌کند، یعنی حافظه **فضای کاربر**.

کرنل برای امنیت جداسازی سخت بین حافظه کاربر و کرنل را اعمال می‌کند. یعنی نمی‌توانیم helperهای فضای کرنلی که قبلاً استفاده کردیم (مثل `bpf_probe_read_kernel_str`) را برای خواندن این داده به کار ببریم. به‌جای آن باید از [bpf_probe_read_user_str(dst, size, src)](https://docs.ebpf.io/linux/helper-function/bpf_probe_read_user_str/) استفاده کنیم.

## کاری که باید انجام دهید

1. pointer filename را از `ctx->args[0]` بسازید.
2. رشته را از **فضای کاربر** به یک بافر محلی بخوانید.

اگر `DEBUG_STR` را روی بافر استفاده کنید، چند برنامه در حال اجرا را می‌بینید.

به یاد داشته باشید که فقط *یک* پاسخ با `SUBMIT_STR_LEN` می‌توانید ارسال کنید، پس باید مثل تمرین‌های قبلی آن‌ها را فیلتر کنید.

می‌توانید `len` را از مقدار بازگشتی `bpf_probe_read_user_str` بگیرید — تعداد بایت‌های کپی‌شده را برمی‌گرداند.
